## Timing and accounting

Four participants start with a common pool of 200 resource units, also its capacity. Each round the mechanism first offers each participant a nonnegative allocation; their sum cannot exceed the current pool. Participants then simultaneously return amounts between zero and their own allocation. Private surplus is allocation minus return. Unallocated resources remain in the pool; returns replenish it at a multiplier of 1.4, capped at 200. We label the pool immediately before the round's allocation as `pool`; `step` returns the pool available for the next round. A zero pool is absorbing.

Experiments 1–3 have 40 decision rounds, without revealing that horizon to participants. The three tutorial rounds are excluded. The payment instructions use a randomly chosen final payable round; mean player surplus in the published figure is nevertheless computed over all recorded rounds, not actual cash payments. A resource point converts to £0.008 in the interface; the reproduced figure reports resource units per player per round. Timeout/dropout games are excluded upstream: after two 90-second timeouts a player would be replaced by a random bot. The release does not recover excluded or missing trajectories.

Experiment 4 has three successive games with the same group, resetting the pool each time. Players know a minimum of 25 rounds followed by a 20% stopping chance, and payment covers the whole realized game. `WorldState` implements only the 40-round Experiments 1–3 scheduler; the accounting function is horizon-free. We do not assign Experiment 4 a 40-round horizon or infer an exact continuation-coin ordering beyond the paper's description.

## Precision, depletion, and unresolved conventions

The human interface increments returns in integers. Therefore an allocation below one permits only zero return. Allocations themselves can be fractional. Behavioral-clone actions are continuous in the released trajectories. `step(integer_contributions=True)` checks the human grid; default continuous mode permits replay of clones. There is no specified rule to round the pool or allocations in the paper, and the released notebook contains no environment implementation. We preserve floating-point allocations and use Python double-precision accounting, without silently rounding, flooring or clipping invalid records. Logged human actions and pool transitions are separately audited in the reproduction.

The paper's physical termination at pool **zero** differs from its analysis threshold: Methods define depletion as pool **below one**, active players as offers **at least one**, and sustainment as the final pool **above one**. The pinned notebook's `find_first_depletion_trial` returns the first pool `< 1` (1-based), or 40 when never depleted; other plotting code uses that derived quantity. These are analysis conventions, not an additional physical law that deletes fractional resources. A numerical runner stops at exact zero or its fixed horizon; `step` permits zero-valued padding for recorded fixed-length trajectories.

For replay, any nonzero tolerance is explicitly a validation allowance, not a data correction: tolerated negative surplus, allocation excess, or transition residual remains visible. The dataset is the source of the figure, so unreleased simulator rounding is not required to recompute Figure 2A; it matters for claims about an exact executable simulator. Replay residuals and any diagnosed source departures belong in the generated analysis report.

### What the recorded transitions actually show

The full 167,782-row audit checks both within-row human `next_environment_state.pool` and the following round's pre-allocation pool, grouped by condition, launch and episode. It uses recorded allocations and returns; it does not substitute reconstructed baseline allocations. Human next-state fields and the following rows agree exactly. All 24,422 human return vectors are integer-valued. No row contains negative offers, negative returns or a return above its offer. Floating-point allocation sums exceed the pool by more than `1e-9` in 1,505 human and 10,032 clone rows; the largest excesses are `2.80e-5` and `3.17e-5` resource units. All rows pass the numerical validation at `1e-4`, with no clipping.

## Allocation baselines

With pool `R`, four players and previous returns `c`, the published mixture allocates `w * R / 4 + (1 - w) * R * c[i] / sum(c)` to player `i`. `w=1` is equal allocation, `w=0` proportional allocation, and `w=0.5` mixed allocation. Every baseline allocates equally initially. The interpolating baseline uses `w=(R/200)**22`, increasingly favoring equality as the pool reaches capacity. The exponent was selected upstream using simulated surplus; EvoPolis does not optimize it in this task.

All four baseline implementations allocate the whole pool. The initial unpublished training collection also used mechanisms that retained resources and a random allocator; those are outside this task. A proportional policy gives a player with zero return zero future allocation while others return positive amounts, creating a route to permanent exclusion. The mixture maintains an equal component; interpolation changes that component with resource abundance.

Task 02's scripted sandbox exposed an implementation precision edge: independently calculated shares could exceed the pool by one floating-point unit, producing a tiny negative next pool when every return was zero. Newly computed baseline allocations now balance the largest share against the remaining shares and, if needed, round that share downward by the smallest representable step. This enforces feasible allocations without adding a pool floor or clipping source records. Recorded replay, its residuals, and the Task 01 artifacts are unchanged.

Neither the paper nor the notebook specifies `sum(c)==0`. We return equal allocations for this denominator edge case and label it an **EvoPolis convention**. At zero pool, the result is unambiguously four zeros. With a full-allocation baseline, zero contributions produce zero next pool, so a positive-pool fallback is normally unreachable after the first round in an exact trajectory. It can become relevant when external mechanisms retain resources or floating-point residuals persist. The first round uses an explicit missing-history marker, not evidence that zero prior contributions occurred.

## Admissible observations

Before choosing a return, a participant sees all four current allocations. At round end the interface shows the pool change, allocations, every return, and everyone's cumulative surplus; participants can remember that public history. The paper describes the BC network input subset as nine values: current allocations, previous returns, and current pool. Inputs are divided by 200. Released player-specific vectors put the focal player first with a cyclic rotation of the remaining slots; `participant_observation` follows this ordering in raw units and uses zero previous returns at initialization.

Neither the fixed undisclosed horizon, another participant's current simultaneous choice, future pool, future returns, group outcomes, nor the hidden recurrent state is available at decision time. `round_index` exists in `WorldState` only for episode bookkeeping and is absent from its observation helper. The helper represents the published BC feature subset; it does not pretend cumulative public surplus was hidden from humans. Task 01's reconstruction performed no behavioral training. [Task 03's new fits](behavioral-agents.md) use these nine inputs with separate resident histories; their learned parameters stay frozen during generated play. Recurrent state updates do not imply online weight adaptation or evolutionary improvement.
